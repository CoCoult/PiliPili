## 二、后端 Bug 修复

### 2.1 ffmpeg 参数 `-vbsf` 已被移除 → 视频转码必然失败

| 项 | 内容 |
|---|---|
| 文件 | `PiliPili-common/src/main/java/com/PiliPili/utils/FFmpegUtils.java` |
| 改动 | `-vbsf h264_mp4toannexb` → `-bsf:v h264_mp4toannexb` |
| 原因 | `-vbsf` 是旧版 ffmpeg 的别名写法，新版（实测 **ffmpeg 9.0.2**）已移除。执行时直接报错：<br>`Unrecognized option 'vbsf'. Error splitting the argument list: Option not found` |
| 现象 | 视频上传后一直「转码失败」，`video_info_file_post.transfer_result = 1` |
| 知识点 | 外部命令版本兼容、ffmpeg bitstream filter、HLS 切片流程 → [§11](#11-外部进程调用与命令注入) |

### 2.2 🔥 Redis 序列化缺 `JavaTimeModule` → 缓存静默失效

> **本项目最有价值的一个 bug，由集成测试发现。**

| 项 | 内容 |
|---|---|
| 文件 | `PiliPili-common/src/main/java/com/PiliPili/redis/RedisConfig.java` |
| 改动 | value 序列化器从 `RedisSerializer.json()` 改为**显式构建** `GenericJackson2JsonRedisSerializer`，并 `registerModule(new JavaTimeModule())` |
| 原因 | `RedisSerializer.json()` 内部的 `ObjectMapper` **没有注册 JavaTimeModule**，一旦缓存对象含 `LocalDateTime`（如 `VideoInfo.createTime`），序列化抛异常：<br>`Java 8 date/time type java.time.LocalDateTime not supported by default`<br>而该异常被 `RedisUtils.setex()` 的 `try-catch` **吞掉**（只打日志）→ **缓存永远写不进去，且不报错** |
| 现象 | 50 并发压测下数据库被查了 **50 次**（互斥锁等于白做）；从缓存读出来是 `null` |
| 知识点 | Redis 序列化方式选型、Jackson 模块注册、**静默失败为什么最危险** → [§3](#3-redis-序列化) |

### 2.3 缓存删除时机：必须放在事务提交之后

| 项 | 内容 |
|---|---|
| 文件 | `PiliPili-common/.../service/impl/VideoInfoServiceImpl.java` |
| 改动 | `deleteVideoInfoCache()` 内部判断 `TransactionSynchronizationManager.isSynchronizationActive()`，在事务中则注册 `afterCommit` 回调延迟删除 |
| 原因 | 若事务未提交就删缓存，其他线程此刻来读会读到**旧数据**并重新写回缓存 → 脏数据长期存在 |
| 知识点 | Spring 事务同步器、缓存与数据库一致性、延迟双删 → [§4](#4-缓存与数据库一致性) |

## 五、性能优化：视频详情缓存（Redis）

### 5.1 背景

`GetVideoInfoByVideoId` 有 **11 处调用方**（视频详情页、弹幕、评论、点赞、消息…），每次都直查 MySQL。视频场景是典型的**读多写少 + 热点集中**，非常适合做缓存。

### 5.2 设计方案：Cache-Aside（旁路缓存）

```
读：先查 Redis → 未命中则查 MySQL → 回写 Redis（带 TTL）
写：更新 MySQL → 删除 Redis 缓存（不是更新缓存）
```

**为什么删而不是更新？** 更新缓存存在并发覆盖问题（两个线程先后写可能把旧值盖回去），删除更简单安全，下次读自然回源。

### 5.3 缓存三件套防护

| 问题 | 触发条件 | 防护手段 | 实现位置 |
|---|---|---|---|
| **穿透** | 查的数据**根本不存在** | 空值缓存（占位对象 + 短 TTL 2 分钟） | `isNullHolder()` |
| **击穿** | 某**一个热点 key** 刚过期 | 互斥锁（`SETNX`）+ 双重检查 + 等待重试 | `GetVideoInfoByVideoId()` |
| **雪崩** | **一批 key** 同时过期 | TTL 加随机抖动（30 分钟 + 0~5 分钟） | `randomSeconds()` |

### 5.4 文件改动清单

| # | 文件 | 改动内容 |
|---|---|---|
| 1 | `PiliPili-common/.../entity/constants/Constants.java` | 新增缓存 key 前缀与 TTL 常量（基础 30min / 抖动 5min / 空值 2min / 锁 10s） |
| 2 | `PiliPili-common/.../redis/RedisUtils.java` | 新增 3 个基础设施方法：`setnx()`（抢锁）、`releaseLock()`（**Lua 原子**校验+删除）、`getExpire()` |
| 3 | `PiliPili-common/.../service/VideoInfoService.java` | 接口新增 `deleteVideoInfoCache(videoId)` |
| 4 | `PiliPili-common/.../service/impl/VideoInfoServiceImpl.java` | **核心**：重写 `GetVideoInfoByVideoId`（缓存读取→抢锁→双重检查→回源→回写→释放锁）+ 4 个私有辅助方法 + 3 处写路径接上缓存失效 |
| 5 | `PiliPili-common/.../service/impl/VideoInfoPostServiceImpl.java` | 审核通过写入正式表后，调用 `deleteVideoInfoCache()` |

### 5.5 两个值得讲的设计决策

**① 播放量变化频繁，不删缓存而是"就地更新"**

`addVideoPlayCount()` 每次播放都会触发。如果每次删缓存，缓存就形同虚设。所以改为**就地更新缓存里的计数字段并保留原 TTL**（`updateVideoInfoCacheField()`）。

- 代价：`read-modify-write` 非原子，高并发下可能丢少量计数
- 兜底：MySQL 才是权威数据源，TTL 到期回源后自动纠正
- 更严格的方案：计数器单独用 Redis `INCR` 维护，读取时再合并

**② 缓存删除放在事务提交后**

见 [§2.3](#23-缓存删除时机必须放在事务提交之后)。

| 依赖 | 处理方式 | 理由 |
|---|---|---|

### 6.4 🎯 测试发现的真 Bug（完整过程）

这是本阶段最有价值的产出，**建议面试时重点讲**：

1. **第一轮**：测试用假数据（不带时间字段）→ **6/6 全过** ✅
2. **第二轮**：给假数据补上真实的 `LocalDateTime` → **5/6 失败** ❌

失败现象：

| 用例 | 现象 |
|---|---|
| 50 并发 | 数据库被查了 **50 次** |
| 缓存失效 | 第二次读未命中缓存，又查了库 |
| 播放量 | 从 Redis 读出 **null** |
| **唯一通过的** | **防穿透**——因为它缓存的是 `new VideoInfo()`，**恰好没有时间字段** |

**根因**：`RedisSerializer.json()` 未注册 `JavaTimeModule` → 序列化 `LocalDateTime` 抛异常 → 被 `try-catch` 吞掉 → **缓存静默失效**。

**修复**：`RedisConfig` 显式构建序列化器并注册 `JavaTimeModule`；同时**让测试复用线上那份序列化器**（`RedisConfig.buildJsonSerializer()`），保证「测的」就是「跑的」。

**修复后**：**6/6 全部通过** ✅，日志可见 TTL 抖动生效：
```
TESTCACHE1      → ttl:1986 / 2029 / 1980 / 1922 / 1874
TESTJIT001~008  → ttl:1994 / 2090 / 1857 / 1804 / 1813 / 2039 / 1982 / 1953
```

> 💡 **教训**：能被 `try-catch` 吞掉的异常，是最难排查的一类 bug。没有测试的话，只能等上线后「发现缓存怎么没效果」才回头查。

## 七、数据库结构与数据修正

### 7.1 字段长度与代码校验不一致（会触发 Data truncation）

控制器 `@Size(max=n)` 允许的长度**大于**表字段长度 → 插入时 `Data truncation: Data too long for column`

| 表.字段 | 原长度 | 改为 | 依据 |
|---|---|---|---|
| `video_info_post.video_cover` | varchar(50) | **varchar(500)** | 封面名实际 53 字符（`COVER/日期/32位随机.png`）→ **这是投稿失败的直接原因** |
| `user.email` | varchar(50) | **varchar(150)** | `AccountController.Register` 允许 150 |
| `user.school` | varchar(50) | **varchar(100)** | `UserCenterController.UpdateUserInfo` 允许 100 |
| `video_barrage.text` | varchar(255) | **varchar(500)** | `VideoBarrageController.PostBarrage` 允许 300 |

### 7.2 删除 user 表冗余列（消除 SQL 列名歧义）

| 项 | 内容 |
|---|---|
| 改动 | `ALTER TABLE user DROP COLUMN play_count, DROP COLUMN like_count;` |
| 原因 | 热榜 SQL 是 `ORDER BY play_count DESC`，而 `user` 表也有 `play_count` 列 → `<br>ERROR 1052: Column 'play_count' in order clause is ambiguous`（接口直接 500） |
| 知识点 | 多表 JOIN 的列名歧义、`ORDER BY` 解析顺序 |

### 7.3 分类字段语义修正

| 项 | 内容 |
|---|---|
| 改动 | `UPDATE video_info SET category_id = p_category_id, p_category_id = 0 WHERE category_id IS NULL;` |
| 原因 | 项目约定（见 `Post.vue`）：**只选一级分区**时 `p_category_id = 0`、`category_id = 一级id`；**选了二级**才是 `p_category_id = 一级id`、`category_id = 二级id`。而分区页查询用的是 `categoryId`，字段填错会导致所有分区页查不到视频 |

### 7.4 推荐位与热榜数据分布

| 项 | 内容 |
|---|---|
| 改动 | 8 个视频 `recommend_type = 1`（首页），30 个 `= 0`（分区页可见）；部分视频写入 `last_play_time` |
| 原因 | `getRecommendVideo` 只查 `recommend_type = 1`，`getVideo` 只查 `= 0`，两者互斥；热榜要求 `last_play_time` 在 24 小时内 |
