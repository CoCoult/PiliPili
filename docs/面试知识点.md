## 1. Redis 缓存三件套（穿透 / 击穿 / 雪崩）

### 1.1 项目背景

视频详情接口 `GetVideoInfoByVideoId` 有 11 处调用方，每次都直查 MySQL。我给它加了 Cache-Aside 缓存，并针对三种异常场景做了防护。

### 1.2 三者的区别（⭐ 最容易被问混）

| 问题 | 触发条件 | 数据是否存在 | 影响范围 |
|---|---|---|---|
| **穿透** | 查询**根本不存在**的数据 | ❌ 不存在 | 每次都打到 DB |
| **击穿** | **某一个热点 key** 刚好过期 | ✅ 存在 | 瞬时并发全部涌向 DB |
| **雪崩** | **一大批 key** 同时过期，或 Redis 宕机 | ✅ 存在 | DB 瞬时被打满 |

> 一句话记忆：**穿透是"数据不存在"、击穿是"一个 key"、雪崩是"一批 key"**。

### 1.3 解决方案

**穿透**
- ✅ **空值缓存**（项目已实现）：查库为空也写一个占位对象，TTL 设短（2 分钟）
  - 为什么 TTL 要短？避免数据后来真被创建了，缓存里还是空标记
- **布隆过滤器**：把所有存在的 id 预先放进位数组；说"不存在"→ 100% 准确直接返回；说"存在"→ 才继续查
  - 优点：极省内存；缺点：**有误判率**、**不支持删除**

**击穿**
- ✅ **互斥锁**（项目已实现）：未命中时先抢 Redis 锁，只放一个线程回源，其他线程等待重试
- **逻辑过期**：缓存不设 Redis TTL，value 里塞 `expireTime`；发现逻辑过期仍**返回旧数据** + **异步线程重建**
  - 优点：永不阻塞，吞吐更高；缺点：返回旧数据
  - 取舍：能接受短暂等待 → 互斥锁；要极致性能 → 逻辑过期

**雪崩**
- ✅ **TTL 加随机抖动**（项目已实现）：`1800 + random(0, 300)` 秒
- 其他：多级缓存（Caffeine 本地 + Redis）、熔断降级、缓存预热、Redis 主从/哨兵、热点 key 永不过期 + 后台刷新

### 1.4 项目实现位置

`PiliPili-common/.../service/impl/VideoInfoServiceImpl.java` → `GetVideoInfoByVideoId()`

### 1.5 常见追问

- **互斥锁的等待线程如果一直等不到缓存怎么办？** → 项目里做了**降级**：重试 3 次（约 150ms）仍失败就直接查库，可用性优先
- **锁的持有时间比业务执行时间长会怎样？** → 锁自动过期后其他线程拿到锁，原线程执行完可能误删别人的锁 → 所以释放锁必须用 Lua 校验 value
- **布隆过滤器为什么不能删除？** → 多个元素共享位，置 0 会影响其他元素 → 可用计数布隆过滤器或定期重建
- **空值缓存和布隆过滤器怎么选？** → 小项目空值缓存够用；有恶意攻击、数据量大的场景上布隆过滤器

## 2. Redis 分布式锁

### 2.1 项目背景

缓存重建需要"同一时刻只放一个线程回源"，用 Redis 实现分布式锁。

### 2.2 正确实现的四个要点（⭐ 缺一不可）

```java
// 1) 抢锁：SET key value NX PX 30000 —— 原子操作，且必须带自动过期（防死锁）
boolean locked = redisUtils.setnx(lockKey, uuid, 10_000L);

// 2) value 必须是唯一标识（UUID），用于第 3 步校验
String lockValue = UUID.randomUUID().toString();

// 3) 释放锁：Lua 保证"判断是否是自己 + 删除"是原子的
//    反例：A 业务超时 → 锁自动过期 → B 拿到锁 → A 执行完把 B 的锁删了
String script = "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end";
redisUtils.releaseLock(lockKey, lockValue);
```

### 2.3 为什么不能用 `SETNX` + 单独 `EXPIRE`

两条命令**不是原子的**——如果 `SETNX` 成功但 `EXPIRE` 之前进程崩溃，锁就永不过期 → **死锁**。
（`SET key value NX PX ms` 是 Redis 2.6.12+ 提供的原子写法）

### 2.4 常见追问

- **锁自动过期了但业务还没执行完怎么办？** → 需要**锁续期**（看门狗机制），Redisson 的 `RLock` 内置了
- **Redis 主从架构下锁会失效吗？** → 会！主节点写入锁后未同步就宕机，从节点升主 → 锁丢失。这是 **Redlock** 想解决的问题，但 Redlock 本身也有争议（Martin Kleppmann vs antirez 的著名辩论）
- **Redisson 怎么实现可重入锁？** → 用 Hash 结构，field 存 `客户端ID:线程ID`，value 存重入次数

## 3. Redis 序列化

### 3.1 项目背景（🔥 血泪教训）

我给缓存加完功能、测试全绿。但当我给测试数据补上真实的 `LocalDateTime` 后，**5/6 个测试集体失败**——50 并发压测下数据库被查了 50 次。

### 3.2 根因

项目用 `RedisSerializer.json()`，它内部的 `ObjectMapper` **没有注册 `JavaTimeModule`**：

```
Java 8 date/time type java.time.LocalDateTime not supported by default
```

更糟的是：这个异常被 `RedisUtils.setex()` 的 `try-catch` **吞掉了**（只打日志），表现为
👉 **缓存静默失效——不报错、不崩溃，但缓存永远写不进去。**

### 3.3 三种序列化方式对比

| 方式 | 优点 | 缺点 |
|---|---|---|
| `JdkSerializationRedisSerializer`（默认） | 无需配置 | 二进制不可读、`Serializable` 约束、**跨语言不兼容**、体积大 |
| `StringRedisSerializer` | 可读、轻量 | 只能存字符串，复杂对象要手动转 JSON |
| **`GenericJackson2JsonRedisSerializer`** ✅ | 可读、跨语言、自动写 `@class` 类型信息 | 需要正确配置 ObjectMapper |

### 3.4 修复

```java
public static RedisSerializer<Object> buildJsonSerializer() {
    ObjectMapper objectMapper = new ObjectMapper();
    objectMapper.registerModule(new JavaTimeModule());                       // ★ 关键
    objectMapper.disable(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS);    // 写成 ISO-8601 而非时间戳
    objectMapper.activateDefaultTyping(                                      // 保留 @class
            objectMapper.getPolymorphicTypeValidator(),
            ObjectMapper.DefaultTyping.NON_FINAL, JsonTypeInfo.As.PROPERTY);
    return new GenericJackson2JsonRedisSerializer(objectMapper);
}
```

> 💡 关键工程实践：**让测试复用线上那份序列化器**（`RedisConfig.buildJsonSerializer()`），否则「测的」和「跑的」是两套东西，测了等于白测。

### 3.5 常见追问

- **`@class` 有什么风险？** → 反序列化任意类型有**安全风险**（类似反序列化漏洞），生产环境可考虑用 `activateDefaultTyping` 的 `PolymorphicTypeValidator` 白名单限制包名
- **`WRITE_DATES_AS_TIMESTAMPS` 开着会怎样？** → 时间存成数字时间戳，可读性差、跨语言解析麻烦

## 4. 缓存与数据库一致性

### 4.1 项目背景

视频信息变更（改互动设置、审核通过、删除视频）时，必须让缓存失效。

### 4.2 为什么"删除缓存"而不是"更新缓存"

| 方案 | 问题 |
|---|---|
| 更新缓存 | **并发覆盖**：线程 A 写新值、线程 B 写旧值，顺序错乱就把旧值盖回去了；且很多场景下缓存是"计算结果"，更新成本高 |
| **删除缓存** ✅ | 简单安全，下次读自然回源重建（Cache-Aside 的标准做法） |

### 4.3 先删缓存还是先更新数据库？

| 顺序 | 问题 |
|---|---|
| 先删缓存，再更新 DB | 删完缓存、DB 还没更新时，其他线程读到旧数据并**写回缓存** → 脏数据长期存在 |
| **先更新 DB，再删缓存** ✅ | 极端情况下仍有小概率不一致（读线程在删除前拿到旧值），所以工业界还有：**延迟双删**、**订阅 binlog（Canal）异步失效** |

### 4.4 项目里的做法：事务提交后再删

```java
public void deleteVideoInfoCache(String videoId) {
    if (TransactionSynchronizationManager.isSynchronizationActive()) {
        // 在事务中就注册 afterCommit 回调 → 等 DB 真正提交后再删缓存
        TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
            @Override
            public void afterCommit() { doDeleteVideoInfoCache(videoId); }
        });
    } else {
        doDeleteVideoInfoCache(videoId);
    }
}
```

**原理**：如果事务未提交就删了缓存，其他线程此刻来读会读到**未提交前的旧数据**并写回缓存 → 脏数据长期存在。

### 4.5 常见追问

- **延迟双删是什么？** → 更新 DB 前删一次、更新后**延迟几百毫秒再删一次**，覆盖"删除瞬间被读线程写回旧值"的窗口
- **Canal 方案怎么做？** → 伪装成 MySQL 从库订阅 binlog，解析出数据变更后发 MQ，由消费者删缓存 → 业务代码零侵入
- **强一致能做到吗？** → 缓存+DB 本质是分布式系统，CAP 下只能做到**最终一致**；要求强一致就加分布式锁或用同一份存储

## 5. Redis 数据结构选型

### 5.1 项目里已用到的（14 处）

| 场景 | 数据结构 | Key |
|---|---|---|
| 图形验证码 | String + TTL | `PiliPili:checkCode:{uuid}` |
| 用户/管理员登录态 | String(JSON) + TTL | `PiliPili:token:web:{token}` |
| 分类缓存 | String(JSON List) | `PiliPili:categoryList:` |
| 系统设置 | String(JSON) | `PiliPili:sysSetting:` |
| 分片上传状态 | String(JSON) + TTL | `PiliPili:uploading:{userId}{uploadId}` |
| **转码任务队列** | **List**（lpush/rpop） | `PiliPili:queue:transfer` |
| 播放上报队列 | List | `PiliPili:queue:video:play:` |
| **搜索热词榜** | **ZSet** | `PiliPili:video:search:count` |
| **在线观看人数** | String + **过期监听** | `PiliPili:video:play:online:{fileId}` |
| 每日播放量 | String 计数 | `PiliPili:video:play:count:{date}:{videoId}` |
| **视频详情（本次新增）** | String(JSON) + TTL | `PiliPili:video:info:{videoId}` |
| 推荐评分矩阵 | String(JSON Map) | `User_SCORE_MATRIX` |

### 5.2 各数据结构的适用场景（面试常问）

| 结构 | 典型场景 | 项目可扩展点 |
|---|---|---|
| String | 缓存、计数器、分布式锁 | ✅ 已用 |
| List | 消息队列、最新列表 | ✅ 已用（可升级 Stream） |
| **Set** | 去重、共同好友（交集）、抽奖 | ⬜ **点赞状态判重**（`SISMEMBER` O(1)） |
| **ZSet** | **排行榜**、延时队列 | ⬜ **热榜**（现在靠 MySQL `order by play_count`） |
| Hash | 对象字段部分更新 | ⬜ 播放进度（`HSET progress:{userId} {videoId} 秒数`） |
| **Bitmap** | 签到、**去重判存在**、布隆过滤器 | ⬜ **上传分片位图**（秒传）、点赞状态（1 亿用户仅 12MB） |
| HyperLogLog | **UV 统计**（有 0.81% 误差） | ⬜ 每日 UV |
| Stream | **可靠消息队列**（消费组 + ack） | ⬜ 替换 List 队列（**需 Redis 5.0+**） |

> ⚠️ 本机 Redis 是 **3.2.100**，`Stream`(5.0+)、`UNLINK`(4.0+) 都不可用。想用高级特性需要升级 Redis。

### 5.3 常见追问

- **ZSet 的底层结构？** → 元素少时用 ziplist，多时用 **跳表(skiplist) + 哈希表**；跳表查询 O(logN)
- **Bitmap 和 Set 存点赞状态怎么选？** → 用户 id 连续且量大 → Bitmap（省内存）；id 稀疏 → Set
- **HyperLogLog 为什么省内存？** → 基于**概率算法**（调和平均数估算基数），12KB 可估算 2^64 个基数，代价是 ~0.81% 误差
- **Redis 单线程为什么快？** → 纯内存操作 + IO 多路复用 + 单线程免锁竞争；6.0 后网络 IO 是多线程的，命令执行仍是单线程

## 6. Spring 事务

### 6.1 项目背景

`VideoInfoPostServiceImpl.SaveVideoInfo` 是 `@Transactional`，但方法内部**同时操作了数据库、Redis 队列、文件系统**。

### 6.2 核心结论

> **`@Transactional` 只能回滚数据库操作，Redis / 文件 / MQ 的操不受事务管理。**

```java
@Transactional(rollbackFor = Exception.class)
public void SaveVideoInfo(...) {
    this.videoInfoPostMapper.InsertVideoInfoPost(...);      // ← DB，可回滚
    redisComponent.SaveInsertVideoFilePost2Queue(...);      // ← Redis，不回滚！
}
```

如果 Redis 推送成功后数据库回滚 → **Redis 队列里留下垃圾任务**。

### 6.3 解决方案

| 方案 | 思路 |
|---|---|
| **事务同步器**（项目采用） | `TransactionSynchronizationManager.registerSynchronization(..., afterCommit)` —— 把外部操作放到提交成功之后执行 |
| **本地消息表** | 外部操作与业务数据写在同一张表，再异步投递（保证最终一致） |
| **事务消息** | RocketMQ 事务消息，两阶段提交 |
| **避免长事务** | 外部调用移出事务方法，事务内只做 DB |

### 6.4 `@Transactional` 失效的常见场景（⭐ 高频八股）

1. **同类内部方法调用**（`this.method()`）→ 不走代理，注解失效
2. **方法不是 public**
3. **异常被自己 try-catch 吞掉** → 不回滚（或需手动 `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()`）
4. **默认只回滚 `RuntimeException`** → 受检异常需 `rollbackFor = Exception.class`
5. **数据库引擎不支持事务**（MyISAM）
6. **多线程调用** → 事务上下文不传递

### 6.5 传播行为

| 传播行为 | 说明 |
|---|---|
| `REQUIRED`（默认） | 有事务就加入，没有就新建 |
| `REQUIRES_NEW` | 挂起当前事务，新建独立事务（**注意：内外层不会一起回滚**） |
| `NESTED` | 嵌套事务，用 savepoint 实现，内层回滚不影响外层 |

## 7. Maven 依赖管理与版本对齐

### 7.1 项目背景

项目父 pom 里写了 `<es.version>3.3.2</es.version>`，但代码用的是 Spring Data ES **4.x** 的 API，最终构建失败。

### 7.2 关键概念

| 概念 | 作用 |
|---|---|
| `<dependencyManagement>` | **只声明版本，不引入依赖**；子模块引用时无需写版本 |
| `<dependencies>` | 真正引入依赖 |
| **版本仲裁规则** | ① 最短路径优先 ② 路径相同时**先声明者优先** |
| **覆盖父 pom** | 子 pom / 当前 pom 的 `dependencyManagement` 优先级**高于**继承来的 |

### 7.3 项目中的表现

`spring-boot-starter-parent:2.7.6` 本已管理好 `spring-boot-starter-data-elasticsearch:2.7.6`（对应 ES 7.17 客户端），
但当前 pom 的 `dependencyManagement` 用 `${es.version}=3.3.2` **覆盖**了它 → 拉来 Spring Boot 3.x 生态的 jar → 与 Java 8 和现有代码都不兼容。

### 7.4 常见追问

- **怎么排查依赖冲突？** → `mvn dependency:tree`、IDEA 的 Maven 依赖图、`mvn dependency:analyze`
- **`optional` 和 `provided` 的区别？** → `optional=true` 不传递；`provided` 不打包（容器提供）
- **依赖下载慢/失败怎么办？** → 配置国内镜像（阿里云）在 `settings.xml` 的 `<mirrors>`；`<mirrorOf>*</mirrorOf>` 镜像所有仓库
- **本地仓库在哪？** → 默认 `~/.m2/repository`，可用 `<localRepository>` 覆盖

## 8. MySQL 数据类型、索引与 SQL 细节

### 8.1 项目背景

投稿功能一直失败，报 `Data truncation: Data too long for column 'video_cover' at row 1`。

### 8.2 根因

| 概念 | 说明 |
|---|---|
| `varchar(n)` 的 n | **字符数**而非字节数（`utf8mb4` 下 1 个中文占 1 字符、最多 4 字节） |
| 长度校验不一致 | 控制器 `@Size(max=150)` 允许 150，但表字段是 `varchar(50)` → 插入必然截断 |
| 严格模式 | `STRICT_TRANS_TABLES` 下超长**直接报错**；非严格模式会**静默截断**（更危险！） |

**排查思路**：把「接口参数校验长度」与「表字段长度」逐一对齐（项目里共发现 4 处不一致）。

### 8.3 列名歧义

```sql
-- user 表也有 play_count 列 → 报错
SELECT ... FROM video_info v LEFT JOIN user u ON ... ORDER BY play_count DESC
-- ERROR 1052: Column 'play_count' in order clause is ambiguous
```

**解决**：加表别名前缀（`ORDER BY v.play_count`）或删除冗余列。

### 8.4 常见追问

- **`varchar` 和 `char` 区别？** → `varchar` 变长（省空间、需 1~2 字节长度前缀）；`char` 定长（适合 MD5、性别等固定长度，无长度前缀、更快）
- **为什么建议用 `utf8mb4`？** → 支持 emoji（4 字节），`utf8` 在 MySQL 里其实是 3 字节的 `utf8mb3`
- **`COUNT(*)` / `COUNT(1)` / `COUNT(字段)` 区别？** → `COUNT(字段)` 不统计 NULL 行；`COUNT(*)` 和 `COUNT(1)` InnoDB 下差别不大
- **深分页怎么优化？** → `WHERE id > 上一页最大id LIMIT n`（游标分页）或延迟关联
- **`EXPLAIN` 关注什么？** → `type`（至少要 range，避免 ALL 全表扫）、`key`（实际用的索引）、`rows`、`Extra`（避免 `Using filesort` / `Using temporary`）

## 9. 测试：单元测试与集成测试

### 9.1 项目背景

项目原本**没有任何测试**（`src/test` 目录不存在）。我加了 `VideoInfoCacheTest`，6 个用例覆盖缓存全部行为——**并且真的抓到了 1 个线上必炸的 bug**。

### 9.2 测试金字塔

```
        /\   E2E（少，慢，贵）
       /──\  集成测试（适中）
      /────\ 单元测试（多，快，便宜）
```

### 9.3 项目里的测试策略

| 依赖 | 处理 | 理由 |
|---|---|---|
| MySQL | **Mockito mock** `VideoInfoMapper`，用 `verify(..., times(n))` 断言回源次数 | 快、稳定、不依赖环境 |
| Redis | **真实实例** | `SETNX`/Lua/TTL 语义 mock 不出来 |
| Redis 未启动 | `Assumptions.assumeTrue(...)` 跳过 | 不在别人机器上跑红 |

### 9.4 三个实用技巧（面试可讲）

**① 用 `verify(times(n))` 断言"回源了几次"** —— 把"缓存有没有生效"变成可断言的事实：

```java
videoInfoService.GetVideoInfoByVideoId(TEST_ID);
videoInfoService.GetVideoInfoByVideoId(TEST_ID);
verify(videoInfoMapper, times(1)).GetVideoInfoByVideoId(TEST_ID);   // ★ 核心断言
```

**② 用 `CountDownLatch` 做并发测试**（验证分布式锁）：

```java
CountDownLatch startGate = new CountDownLatch(1);   // 所有线程在这里等
CountDownLatch endGate = new CountDownLatch(n);     // 等所有线程结束
for (int i = 0; i < n; i++) {
    pool.execute(() -> {
        startGate.await();                          // 一起放行，制造真并发
        videoInfoService.GetVideoInfoByVideoId(TEST_ID);
        endGate.countDown();
    });
}
startGate.countDown();
endGate.await(20, TimeUnit.SECONDS);
verify(videoInfoMapper, times(1)).GetVideoInfoByVideoId(TEST_ID);   // 50 并发只回源 1 次
```

**③ 让测试复用生产代码**（本项目最关键的实践）：

```java
// 测试里直接用线上那份序列化器
redisTemplate.setValueSerializer(RedisConfig.buildJsonSerializer());
```
> 否则「测试验证的」和「线上跑的」是两套东西——本项目正是因为**补上真实时间字段**才暴露出序列化 bug。

### 9.5 常见追问

- **单元测试和集成测试的区别？** → 单元测试隔离依赖（mock）；集成测试验证多组件协作（真实 DB/Redis）
- **Mockito `@Mock` 和 `@Spy` 区别？** → `@Mock` 全部方法返回默认值；`@Spy` 默认调用真实方法
- **`when(...).thenReturn(...)` 和 `doReturn(...).when(...)` 区别？** → 后者不执行真实方法，适合 spy 或抛异常场景
- **为什么测试要能"跳过"？** → 依赖外部环境的集成测试，缺环境时应 `Assumptions.assumeTrue` 跳过而不是失败，否则 CI 会无谓变红

## 10. Vue3 响应式原理

### 10.1 项目背景

投稿页编译报错：`Cannot assign to "inputValue" because it is a constant`。

### 10.2 根因

```javascript
const inputValue = ref();     // ref 返回的是一个「包装对象」
inputValue = "";              // ❌ 等于给常量重新赋值（编译期就被 esbuild 拦下）
inputValue.value = "";        // ✅ 改的是包装对象内部的 value
```

### 10.3 `ref` vs `reactive`

| | `ref` | `reactive` |
|---|---|---|
| 适用 | 基本类型、任意类型 | **对象/数组** |
| 访问 | 脚本里要 `.value`；**模板里自动解包** | 直接访问属性 |
| 丢失响应式 | 不会 | 解构 / 重新赋值整个对象会丢失 |
| 实现 | `RefImpl` 类 + `get/set` 拦截 | `Proxy` 代理 |

> 💡 `reactive` 基于 `Proxy`，只能代理对象；`ref` 底层也是把值包成对象再用 `Proxy`（或 `defineProperty`）实现。

### 10.4 为什么模板里不用写 `.value`

Vue 编译器在编译模板时，会从 `<script setup>` 的**绑定元数据**里得知某个变量是 ref，编译成 `$setup.inputValue.value`。

**有意思的是**：模板里 `showViewer = false` 这种写法**能正常工作**——因为 `$setup` 是经过 `proxyRefs()` 包装的，它的 `set` 陷阱会自动把赋值转成 `xxx.value = ...`。**但脚本里（`<script setup>` 内）没有这层包装，必须手写 `.value`**。

### 10.5 常见追问

- **`ref` 为什么需要 `.value`？** → JS 无法监听基本类型的值变化，只能包一层对象做拦截
- **`toRefs` / `toRef` 有什么用？** → 把 reactive 对象的属性转成 ref，解构后仍保持响应式
- **`computed` 和 `watch` 区别？** → `computed` 有缓存、依赖不变不重算；`watch` 是副作用、可异步
- **`v-model` 在组件上怎么实现的？** → 语法糖：`:modelValue` + `@update:modelValue`

## 11. 外部进程调用与命令注入

### 11.1 项目背景

项目用 `Runtime.exec()` 调 ffmpeg 做视频转码，而新版 ffmpeg 移除了 `-vbsf` 参数，导致转码全部失败。

### 11.2 现有实现的问题（可优化点）

```java
// ProcessUtils.java
if (osName.contains("win")) {
    process = Runtime.exec(cmd);          // ① 拼接字符串，有注入风险
}                                         // ② 没有超时，ffmpeg 卡住会拖死线程
process.waitFor();
```

| 问题 | 说明 | 改进 |
|---|---|---|
| **命令注入** | `cmd` 里拼接了用户上传的**文件名**，含 `&`/`|`/`"` 等字符可执行任意命令 | 用 `ProcessBuilder` 传**参数数组**，不做 shell 拼接 |
| **无超时** | ffmpeg 处理大文件或损坏文件可能永久阻塞 | `process.waitFor(timeout, unit)` + `destroyForcibly()` |
| **流未及时消费会阻塞** | 子进程输出缓冲区满后子进程会卡住（项目里起了两个线程读流，这点做对了 ✅） | 继续保留 |
| **退出码未校验** | 只看输出不看 `exitValue()` | 校验 `exitValue() == 0` |
| **无重试** | 转码失败只置一个状态位 | 加重试 + 死信队列 |

### 11.3 ffmpeg / HLS 相关知识点

| 概念 | 说明 |
|---|---|
| **HLS** | HTTP Live Streaming，把视频切成 `.ts` 分片 + `index.m3u8` 索引，支持边下边播 |
| **为什么切片** | 支持拖动进度、按需加载、适配不同码率 |
| **`h264_mp4toannexb`** | H.264 在 MP4 里用 AVCC 格式（长度前缀），在 TS 里用 Annex-B 格式（起始码 `0x000001`），需要 bitstream filter 转换 |
| **`-vbsf` vs `-bsf:v`** | 旧别名 vs 新写法，新版 ffmpeg 已移除旧别名 |

### 11.4 常见追问

- **`Runtime.exec(String)` 和 `ProcessBuilder` 区别？** → 前者按空格拆分且走平台 shell 语义（Windows 上行为不同），后者参数分离、可设工作目录/环境变量/重定向
- **怎么防止命令注入？** → 不拼字符串，用参数数组；必要时对参数做白名单校验
- **为什么必须消费子进程的 stdout/stderr？** → 管道缓冲区（通常 4KB~64KB）写满后子进程会阻塞在写操作上，导致 `waitFor()` 永久等待
